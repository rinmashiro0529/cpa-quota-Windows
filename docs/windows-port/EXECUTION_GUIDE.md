# 开发执行、协作与交接

## 1. 从真实状态开始

首次接手先读根 [AGENTS.md](../../AGENTS.md)、企划书、来源基线、功能矩阵和所选任务专题。检查当前分支、工作区改动、任务登记、已合并PR和对应CI；不要仅凭上次聊天摘要判断进度。

任务状态权威文件为 [tasks.json](../../planning/tasks.json)。初始应用任务均未完成。状态：planned、ready、in_progress、blocked、in_review、done。准备工作不等于功能完成，文档也不能证明应用已验证。

## 2. 认领与并行

每个任务记录：

- WP编号、owner、起始SHA与分支。
- 对应F-*功能、INV-*不变量及AT-*验收。
- 本次允许修改的模块/文件。
- 交付物、依赖、测试入口与外部阻塞。
- 当前状态、最后进展、下一动作、PR链接。

认领先检查依赖是否done。可提前做不依赖未完成结果的研究或fake，但不能把未经集成的结果标为任务完成。一次PR可覆盖少数紧密相关任务；不得把几十项未验收工作放进一个不可审查的大PR。

任务登记的owner更新通过小提交/PR协调。并发变更同一登记文件时按最新main重放，不能覆盖他人的状态。公共接口和schema由集成负责人统筹，执行者不擅自创建平行版本。

## 3. 推荐工作线

| 工作线 | 主要责任 |
| --- | --- |
| 合同与业务 | Domain/Application、源行为、fixture、状态机 |
| 数据与协议 | HTTP、provider、凭据、SQLite、附件、迁移 |
| Windows与UI | WinUI、输入、窗口、系统展示、通知、发布 |
| 集成与验收 | 公共接口、PR顺序、CI、证据和风险 |

代码和纯测试可以并行；使用同一交互桌面的原生UI任务串行。大型基准/长时间运行在专用或本地测试机有界执行，云端仅运行短、有上限、与具体风险相关的场景。

## 4. 每个PR的内容

必须解释：用户问题、行为变化、源合同对应、实现边界、测试及未运行项。附F/WP/INV/AT编号，准确head SHA，依赖PR，数据/schema变化和升级策略。

PR完成定义：

1. 代码与所属模块边界一致。
2. 源行为和计划要求有测试覆盖，新增测试能发现实际失败而非复述实现。
3. 页面涉及的输入、焦点、缩放、无障碍与失败状态有原生证据。
4. 文档和任务登记对应实际实现。
5. 构建/测试指向同一候选SHA；失败未被跳过或以历史结果替换。
6. 未解决发布阻塞项不以done交付。

源服务、iOS导出配套PR在各自仓库提交，Windows任务登记链接准确仓库与SHA。没有上游代码合并/版本可用证据时保留依赖阻塞。

## 5. 执行工具约定

WP-001建立Windows构建脚本和工具链锁，WP-027建立测试/打包证据入口。当前文档中的未来路径是交付目标，不是现成可执行脚本。

实现期推荐命令入口统一为PowerShell脚本：build、verify、package、collect-evidence；具体参数及可复制命令由建立该脚本的PR写入README。脚本应有超时、架构/配置参数、明确退出码、日志路径和工具链版本记录。

CI使用合成账号、合成token、本地模拟服务。不得通过健康检查、构建步骤或截图测试发送真实付费生成。外部秘密不进入repo/测试fixture/录屏/日志。

## 6. 失败、阻塞与重试

- failed：测试或运行已启动并实际失败，保留原日志和attempt。
- not_run：环境、权限或资源使测试没有执行，不能称通过。
- blocked：明确依赖、负责人和解除条件。
- unknown：外部写入/发送结果无法判断，保留操作ID并先对账。

只针对已诊断的环境故障做有界重跑。不能不断重试直到偶然通过，也不能删断言、增加全目录忽略或放宽TLS/签名/安全设置来取得绿灯。

## 7. 范围与决策变更

来源基线、功能删减、原生技术、数据库格式、凭据策略、远程监控或发布身份的变化须有ADR。记录事实、取舍、替代、迁移和验收影响，更新全部相关文档及任务。

基础实施细节可由执行者按合同自主决定；没有必要对每个可逆选项请求用户确认。涉及真实账户权限、第三方申请、生产部署或计费时，按实际任务授权准备到可审查状态后再处理所需步骤。

用户明确改动目标时其指令优先；计划同步修改，不能引用本文件阻止合法变更。

## 8. 交接模板

交接必须包括：

- 当前目标、基线与分支。
- 已落地提交/PR/运行链接。
- 已通过、失败、未运行的验证及证据位置。
- 剩余风险和外部依赖。
- 下一个可执行动作与阻塞条件。
- 有意保留的工作区改动。

禁止“基本完成”“应该没问题”作为状态。继任者应能仅凭仓库、任务登记和证据恢复工作。

## 9. 计划自身的验证

运行 [validate_plan.py](../../tools/planning/validate_plan.py) 检查链接、feature/acceptance ID、任务DAG与覆盖关系。修改 tasks.json 后运行 [render_backlog.py](../../tools/planning/render_backlog.py) 的 --write 同步 BACKLOG，并以 --check 检查视图一致性。它们不编译Windows应用、不测试真实通知、不证明产品合格。计划校验结果须与应用验收结果严格区分。
